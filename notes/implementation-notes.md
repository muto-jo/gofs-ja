# 実装メモ（サンプル作成）

サンプルデータ作成中に相談した疑問・仕様の解釈・最終的な判断の記録。

## タグ

各記録に 1 つ付ける。掲載先の判断に使う。

| タグ | 内容 | 掲載 |
|---|---|---|
| リファレンス誤り | 実装して分かった、リファレンス（JSON スキーマを含む）自体のミス。translation-notes.md にも記録する | 最終的に MobilityData に Issue を立てる。記事・GitHub に注意として載せる |
| 実装方針 | GOFS で実サービスを表すにあたって確認を要した点。仕様の解釈や、仕様で表せないことに関わるもの | 記事・GitHub に載せる |
| プロジェクト方針 | このプロジェクトのサンプル固有の決め事（題材、値の選び方など） | 載せない |

### I-001 operator に事業主体・運行事業者・システム提供者を区別して書けない
- タグ: 実装方針
- 対象: system_information.json / `name`, `short_name`, `operator`
- 実サービスの状況: 日本のデマンド交通では、事業主体（自治体）・運行事業者・運行システムの提供者が別であることが多い。例えば「のるーとふじ」は、事業主体が富士市、運行事業者が富士急静岡バス株式会社、運行システムがのるーと
- 疑問: `operator` には誰を書くべきか。また、3 者の関係を GOFS で表せるか
- 検討・解釈: `operator` は OPTIONAL の String が 1 つだけで、「Name of the on-demand service operator. The operator name MAY be the same as the system name.」とあるのみ。役割を区別する仕組みは無い。system は、`name` が乗客に表示する名前であることなどから、バックエンドのシステムではなく利用者から見た運行サービス全体と読める。そのため、のるーとのシステムを使って富士市で運行している「のるーとふじ」は、「のるーとふじ」として 1 つの system に定義してよい。GTFS の `attributions.txt` のように、組織ごとに producer・operator・authority の役割を付けられる仕組みを GOFS にも組み込んだほうがよい
- 結論: 現状の仕様では、のるーとふじの場合 `name`: のるーとふじ、`short_name`: 省略またはのるーとふじ、`operator`: 富士市 が妥当と訳者は考える。ただし `operator` を運行事業者（富士急静岡バス株式会社）とするのが妥当という意見も考えられる
  - 役割の区別の仕組みを MobilityData に意見するかは、いったんこのメモに留める（2026-11-18）。重要なのは、利用者から見て事業主体・運行主体・システム提供者を区別する必要があるかどうかであり、現時点ではその必要性がはっきりしないため
- 状態: 決定（2026-11-18）

### I-002 日本のタクシーの時間距離併用運賃を fares.json で正確に表せない
- タグ: 実装方針
- 対象: fares.json / Fare オブジェクトの `start`, `end`、`kilometer`, `minute`, `active_minute`, `idle_minute`
- 実サービスの状況: 日本のタクシーは初乗距離が端数のある距離で決まっている（例: 金沢交通圏の初乗運賃は 1,220m まで 700 円）。また時間距離併用制運賃で、時速 10km 以下の低速走行・停止中は時間による加算に切り替わり、距離による加算は止まる（厳密には、時間を距離に換算して併算する）。金沢交通圏の初乗運賃・加算運賃の出典: GO 公式サイト「石川県のタクシー料金」https://go.goinc.jp/search/ishikawa （確認日 2026-11-10。初乗運賃 1,220m まで 700 円、以降 226m ごとに 100 円）。時間距離併用運賃の出典は未記入
- 疑問: fares.json でこの運賃を表せるか
- 検討・解釈: 次の 3 点で表しきれない
  1. `start` / `end` が Non-negative Integer なので、1.22km のような小数の距離を区間の境目にできない（T-023）
  2. `idle_minute` は「車両が停止している、または動いていない間」の 1 分あたりの価格とされ、低速走行が含まれない。日本の運賃に合わせるには、`idle_minute` の対象に低速走行（例: 時速 10km 以下）を加えてほしい
  3. fares.json はシステムで運賃を計算する方法を定めるもので、総額は `rider` の基本価格に `kilometer`・`minute`・`active_minute`・`idle_minute` の区分を加算したものとされる。日本の運賃は低速時に距離の加算が止まって時間に切り替わる（時間を距離に換算する）ため、各区分の単純な合算では正確に計算できない
  4. 原文の「plus the addition of all relevant segments in `kilometer`, `minute`, `active_minute`, and `idle_minute`」が、4 つの区分を常に並列に適用して合算することを意味するのか、一定の条件で加算のルールを切り替えることも想定しているのかが分からない
  - `realtime_booking` で特定の移動についてより正確な費用の見積もりを返せることを考えると、fares.json は運賃の計算ルールの提示と簡易的な計算のためのものと思われる。特に `active_minute` / `idle_minute` は実際に走ってみないと分からない値である
- 結論: いったんこのメモに留め、MobilityData には意見しない（2026-11-18）。fares.json は計算ルールの提示・簡易計算向けと考え、正確な運賃は `realtime_booking` の見積もりに任せる。北多摩交通圏のサンプルでは時間による加算を含めていない（I-005）
- 状態: 決定（2026-11-18）

### I-003 迎車料金・予約料金・割増料金を定義できない
- タグ: 実装方針
- 対象: fares.json
- 実サービスの状況: 日本のタクシーには、迎車料金、予約料金、深夜早朝などの割増料金がある。出典 URL・確認日は未記入
- 疑問: これらを fares.json で表せるか
- 検討・解釈: fares.json で定義できるのは `rider` の基本価格と、距離・時間（`kilometer`・`minute`・`active_minute`・`idle_minute`）による加算だけで、迎車・予約などの付加料金や、時間帯による割増を定義する仕組みが無い
  - 迎車料金・予約料金は、乗車ごとに 1 回かかる定額の料金なので `rider` で定義できる。どう入れるかは実装ごとの判断でよい（北多摩交通圏のサンプルでは迎車料金を `rider` に入れた。I-006）
  - 深夜早朝などの割増は、時間帯によって運賃全体が変わるルールで、`rider` や距離・時間の区分では表せない
  - GBFS の pricing_plans.json には、料金プランを乗客向けに文章で説明する `description` フィールドがある。fares.json にも同様の説明のフィールドがあれば、構造化して表せない料金（割増の条件など）を文章で伝えられる
- 結論: MobilityData に意見する（2026-11-18）。内容は、割増のルールを定義できるようにしてほしいこと、あわせて GBFS の `description` のような料金の説明のフィールドがあるとよいこと。迎車料金・予約料金は `rider` で定義できるので、意見には含めない
- 状態: 決定（2026-11-18）

### I-006 迎車料金を `rider` で 600 円とする
- タグ: プロジェクト方針
- 対象: fares.json / `rider`
- 実サービスの状況: GO 公式サイトの料金ページに迎車料金の記載は無い。GO サポート＆ガイド「アプリ手配料の対象エリア・タクシー会社について」（2026/11/16 時点）には、タクシー会社ごとの「迎車料金・アプリ手配料」が載っており、小平市周辺の会社（例: 小平交通、小金井交通、新立川交通）は 600 円（迎車料金 500 円・アプリ手配料 100 円）
- 検討・解釈: fares.json には迎車料金に当たる区分が無い（I-003）。`rider` は「乗客 1 人あたりの基本価格」で、総額は `rider` に距離・時間の区分を加算したものなので、乗車ごとに 1 回かかる定額の料金として入れる
- 結論: `rider` を 600 円とした（迎車料金 500 円とアプリ手配料 100 円の合計）。呼ぶ会社によって金額が異なる点は I-014 に記録した
- 状態: 決定（2026-11-17）

### I-009 ポリゴンの作り方
- タグ: 実装方針
- 対象: zones.json / `geometry`（作成スクリプト: `tools/build_zones.py`）
- 実サービスの状況: 北多摩交通圏は 15 市からなる。東京都のうち島しょ部（大島町、利島村、新島村、神津島村、三宅村、御蔵島村、八丈町、青ヶ島村、小笠原村）は降車ゾーンから除く
- 検討・解釈:
  - 境界は国土数値情報 行政区域データ（N03、2026年1月1日時点）を使う（出典表を参照）
  - `kitatama` は 15 市の和集合で、そのまま 1 つの Polygon になる。武蔵村山市の中に瑞穂町の飛び地（約 1.5 万 m²）があり、これは穴として残した
  - `tokyo_mainland` は、島しょ部を除く 53 区市町村と東京湾内の所属未定地の和集合。東京湾の埋立地（お台場、中央防波堤など）が運河で分かれて 92 個の Polygon になる。GOFS の `geometry` は Polygon しか認めない（T-003）
  - 初稿では、クロージング（500m 外側に広げてから 500m 縮める）で運河を埋めて 1 つの Polygon にしたが、水面などを含んで面積が約 3% 増えた
  - ユーザーの判断で、先行実装の ridefreebee の zones.json と同じく、飛び地は本体から線をたどって飛び地を一周し、同じ線を戻る形（往復線）で 1 つの Polygon の外周に含める方法に変えた（T-003 の実例）。往復線が他の飛び地を横切らないよう、つないだ部分に最も近い飛び地から順につなぐ
  - 1ha（10,000 m²）未満の飛び地（岩礁・中州など 74 個、計 約 0.03 km²）と穴（市区町村界のすき間で簡略化後に潰れたものなど）は除いた。残った飛び地は 17 個。北多摩の瑞穂町の飛び地（約 1.5ha）はこの基準でも穴として残る
  - 伊豆・小笠原諸島の所属未定地は除いた
  - どちらも許容誤差 10m で簡略化し（頂点数は `kitatama` 899、`tokyo_mainland` 3,228）、座標は小数点以下 6 桁（約 0.1m）に丸めた
  - 外周リングは反時計回り、穴は時計回りにした。GOFS の本文は逆の向きを書いているが、RFC 7946 と原文の例はこの向きである（T-003）
  - 往復線でつないだ Polygon は自己接触するため、OGC の基準では無効なジオメトリ（Ring Self-intersection）になる。`tools/validate.py` では、線が交差していないこと（そのまま計算した面積と修復後の面積が一致すること）を確かめたうえで、エラーではなく情報として表示するようにした
- 結論: 飛び地は往復線でつなぐ。`tokyo_mainland` の面積は約 1,784 km²（水面を含まない）
- 状態: 決定（2026-11-17）

### I-010 運賃の課金がどの時点で発生するかが定義されていない
- タグ: 実装方針
- 対象: fares.json / `kilometer` の `start`, `end`, `interval`
- 実サービスの状況: 初乗運賃 1000m まで 500 円、以後 211m ごとに 100 円
- 検討・解釈:
  - `amount` は `interval` ごとの額と解釈する（T-013、2026-11-09 の決定）
  - 初乗運賃は `rider` を迎車料金に使うため（I-006）、`kilometer` の最初の区分 `{"start": 0, "end": 1, "interval": 1, "amount": 500}` で表した。初乗距離が 1000m ちょうどなので、`start` / `end` が整数でなければならない問題（T-023）は起きない
  - 加算運賃は `{"start": 1, "interval": 0.211, "amount": 100}` とした
  - 例えば `interval` が 0.211 のとき、その区間に入った時点で課金されるのか、区間を走り終えた時点で課金されるのかは原文に書かれていない。どちらで計算するかはシステムによると考えられる。fares.json は、運賃のルールの表示や簡易的な計算のために定めるものと思われる
- 結論: 課金の時点は不明のまま、定義としては誤っていないので上記の表し方とする。不明であることを記録として残す
- 状態: 決定（2026-11-17）

### I-014 呼ぶタクシー会社によって迎車料金が異なる
- タグ: 実装方針
- 対象: fares.json / `rider`、realtime_booking / `travel_cost`
- 実サービスの状況: GO サポート＆ガイド（2026/11/16 時点）では、同じ北多摩交通圏でも、迎車料金とアプリ手配料の合計が会社によって異なる（例: 小平交通・小金井交通は 600 円、京王タクシー北多摩・イースタンモータース調布は 500 円）。「今すぐ呼ぶ」では、どの会社の車両が手配されるかは配車が決まるまで分からない
- 疑問: GOFS で、手配される会社によって変わる迎車料金をどう表すか
- 検討・解釈: fares.json の運賃は運行ルールごとに `fare_id` で 1 つを指定する仕組みで、手配される会社によって変わる料金を表せない。会社ごとに運行ルールや運賃を分けても、乗客は会社を選べないので、どれが適用されるかを示せない。配車が決まった後の見積もりであれば、`realtime_booking` の `travel_cost` に反映できる可能性がある
  - この問題は、GOFS のフィードを誰が作るかによって変わる。今回は GO をもとにしたため、呼ぶ会社によって迎車料金が異なることになった。タクシー会社（運行事業者）が自社のフィードを作るのであれば、迎車料金はその会社の 1 つの値に決まり、`rider` で表せる。GO のような配車システムの提供会社が、複数の会社をまとめてフィードを作る場合に、会社ごとの違いをどう表すかが問題になる（I-001 の、system と operator の関係の論点とも関わる）
  - 配車システムの提供会社がフィードを作る場合の案として、サービスブランドをタクシー会社ごとに分ける方法がある。GO サポート＆ガイド「タクシー会社を指定して配車することはできますか？」（https://support.go.goinc.jp/hc/ja/articles/25883320004377 、2026-11-17 確認）によると、「今すぐ呼ぶ」でもアプリの「車両・会社を選ぶ」からタクシー会社を指定して配車できる（「AI予約」「GO PREMIUM」では指定した会社を優先して配車し、見つからなければ他社の車両が来ることがある。「タクシー・ライドシェア」を選んでいる場合は会社を指定できない）
  - この案で解決すること
    - 会社ごとにブランド（例: `kodaira_kotsu`、`keio_kitatama`）と運賃（`fare_id`）を作り、運行ルールで組み合わせれば、会社ごとの迎車料金（600 円、500 円など）をそれぞれ 1 つの値で表せる
    - サービスブランドは「乗客が利用できるサービス」と定義されており、乗客が会社を選べる以上、会社をブランドにしても意味が通る
    - 運行ルールでブランドとゾーンを組み合わせるので、会社ごとの営業区域も表せる
    - `wait_time` / `realtime_booking` はブランド（`brand_id`）ごとに結果を返すので、会社ごとの待ち時間や見積もりも返せる
  - この案でも残ること
    - GO の既定は会社を指定せず近くの車両を呼ぶ方式なので、「会社指定なし」のブランドも必要になる。そのブランドの迎車料金は手配される会社によって変わるため、問題はそのブランドに集約されるだけで、なくならない
    - 「タクシー・ライドシェア」を選んだ場合も会社を指定できないので、同じ問題が残る
    - 東京都だけで約 90 社あり、ブランドの数が多くなる（GO アプリの会社選択の画面と同じ構造ではある）
    - 車両タイプの指定（JPN TAXI、大型など）は `vehicle_types` で表せるので、会社をブランドにしても車両タイプとは重ならない
- 結論: 実装にあたっての要確認点として記録する。フィードを作る主体（配車システムの提供会社か、運行事業者か）によって、迎車料金の考え方が変わることに注意する。配車システムの提供会社が作る場合は、タクシー会社ごとにブランドを分けると「会社指定あり」の配車は正確に表せる。「会社指定なし」の配車は、代表的な金額を入れるか、配車が決まった後の金額を `realtime_booking` の `travel_cost` で返すしかないと考える。サンプルは GO をもとにしたが、ブランドは分けず、代表的な金額（600 円）を `rider` に入れた（I-006）
  - これは仕様の不足ではなく、フィードを作る側がブランド（`brand_id`）をどう設計するかの問題なので、MobilityData には意見せず、このメモに留める（2026-11-18）。知見としては上の記述で十分とする
- 状態: 決定（2026-11-18）

### I-017 booking_rules.json に `brand_id` が無く、ブランドごとに予約できる時刻を変えられない
- タグ: 実装方針
- 対象: booking_rules.json
- 実サービスの状況: GO 公式サイト「GO《ゴー》のサービス紹介」（https://go.goinc.jp/service 、2026-11-18 確認）によると、同じ GO アプリでも機能によって予約できる時刻が異なる
  - 「今すぐ呼ぶ」: リアルタイムの配車依頼
  - 「AI予約」: 最短 15 分後から 7 日後までの日時を指定できる
  - 「GOエコノミー」: 当日 10 分前から 2 日後までの日時で予約できる（運行時間は全日 7:00 頃〜25:00 頃。利用可能エリアは都心の 15 区）
  - 「GO PREMIUM」の事前予約・貸切: 1 週間前から当日 1 時間前まで予約できる
- 疑問: これらの機能をサービスブランドに分けたとき、ブランドごとの予約のルールを booking_rules.json で表せるか。booking_rules に `brand_id` があったほうがよいか
- 検討・解釈:
  - booking_rules.json の予約ルールは `from_zone_ids` / `to_zone_ids`（ゾーン）だけで決まり、`brand_id` が無い。operating_rules.json には `brand_id` があり（省略時はすべてのブランドに適用）、`wait_time` / `realtime_booking` もブランドごとに結果を返すのに、予約のルールだけはブランドを指定できない
  - 同じエリアで「今すぐ呼ぶ」（`booking_type=0`）と「AI予約」（`booking_type=1` で `prior_notice_duration_min` / `prior_notice_duration_max` を指定）を両方提供すると、どの予約ルールがどのブランドに当てはまるかを示せない
  - 回避策として、同じ範囲のゾーンをブランドごとに別の `zone_id` で重ねて定義する方法や、ブランドごとに別のフィード（system）に分ける方法が考えられるが、どちらもゾーンやシステムの本来の意味から外れる
  - operating_rules.json と同じく、booking_rules に任意の `brand_id`（省略時はすべてのブランドに適用）があれば素直に表せる
- 結論: booking_rules に `brand_id` があったほうがよいと考える。北多摩交通圏のサンプルはブランドが「今すぐ呼ぶ」の 1 つだけなので影響しない。MobilityData への意見の候補とする
- 状態: 未決
